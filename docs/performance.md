# 网页性能测试

`tests/perf.test.mjs` 用正式构建（和 Cloudflare Pages 相同的 `build.sh`，不带测试短文）打开全站每个页面，手机（390 宽）和电脑（1280 宽）各一次（Chromium），检查：

| 检查 | 规则 | 2026-10-30 实测 |
| --- | --- | --- |
| 首屏下载量 | 到 `load` 事件为止下载的字节数，文本按 gzip 计（接近 Cloudflare 的实际传输量），分 HTML、样式表、脚本、单张图片、合计各有预算 | 普通页面合计最多 111 KB（短文栏目第 2 页，电脑），HTML 最多 15 KB；S-1「风险因素」章 434 KB（HTML 404 KB）；样式表 9 KB；脚本最多 3 KB；单张图片最大 55 KB |
| 请求数 | 不超过 15 | 最多 7 |
| 第三方请求 | 只允许公式/图表的 CDN（`cdn.jsdelivr.net`）和正式站的访问统计（`static.cloudflareinsights.com`） | 没有 |
| 404 | 加载的资源都存在 | 没有 |
| 阻塞渲染 | `<head>` 里的样式表只有站点样式表（有公式的页面加 KaTeX），外部脚本都是 `defer`/`async`/`module` | 符合 |
| 布局偏移 | 加载过程中的累计布局偏移（CLS）不超过 0.1（Web Vitals「良好」线） | 最多 0.035 |

## 为什么只查这些

这些量每次运行结果都一样，可以作为每个 PR 的硬性门槛。首屏多快出来、主线程卡多久这类耗时指标（Lighthouse / PageSpeed Insights 的分数）同一页连跑几次也会差几分，而且 PageSpeed Insights 只能测已上线的网址、依赖外部服务，适合定期看趋势，不适合拦 PR。耗时指标的主要成因（下载量、请求数、阻塞渲染的资源、第三方请求）都在上面的检查里。

普通页面的量和 PaperMod 本身相当：一个样式表、没有外部脚本、HTML 十几 KB。

## 超出预算时

失败信息会列出页面、手机还是电脑、哪一项、实际值和预算。

- 确实是退步（多引入了一个库、原图没压缩、样式表翻倍）：修掉。
- 内容本来就该更大（例如新译文章节更长）：改 `tests/perf.test.mjs` 开头 `BUDGET` 里对应的一行，并更新上表的实测值。`html`、`total` 按路径前缀取预算，可以只给某个栏目放宽。
- 要允许新的第三方网站：加进 `THIRD_PARTY`，并说明是哪个功能用的。

## 已知情况

- S-1 的短章节（如「股利政策」）在电脑上偶尔有 0.035 的布局偏移：默认原版版式在加载时插入，页脚的翻页条被推下去。时有时无，取决于插入前有没有画过一帧，在「良好」线以内。
- 只用 Chromium：WebKit 没有布局偏移的接口，下载量和请求数两个浏览器一样。

## 本地运行

```bash
cd tests && npm ci && npx playwright install chromium
node --test perf.test.mjs   # 约 40 秒，输出里有各项的实测最大值
```
